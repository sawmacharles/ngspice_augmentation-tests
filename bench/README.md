# bench/ -- transient-ACCELERATION benchmark set (card #467/#478/#483/#486, plan T9.1/T9.2/T9.3/T9.4)

Four synthetic decks (card #467, plan T9.1), chosen to cover the workload
shapes named in the card: device-eval-dominated PEX-sized, long switching
transient, many-point campaign (two run modes), and a many-BSIM4-transistor
analog block, plus two more (card #478, plan T9.2, round 2) added to close
gaps the round-1 profile found: a tree-shaped PEX net (`e_pex_tree`, task 2)
and a longer-running variant of the analog block (`d_analog_block_long`,
task 3, needed so an OMP-schedule change has enough Newton iterations for a
stable signal), plus two more (card #483, plan T9.3, round 3) exercising a
different OpenMP device loader (BSIM3 instead of BSIM4): `f_analog_block_bsim3`
and `f_analog_block_bsim3_long`, plus one more (card #486, plan T9.4, round 4)
covering every B-source parser function/operator for the forward-mode-AD
candidate: `g_ad_stress`. None of this is derived from or read out of
any real design (#454 A) -- everything
here is a plausible synthetic stand-in, generated by the `gen_*.py` scripts
in this directory. **Do not hand-edit the generated `.cir` files under
`decks/`** -- regenerate them from the generator instead; the generators are
the source of truth and are the things to change if a deck needs to be
bigger/smaller/different.

## The decks

| deck | generator | what it stresses | size |
|---|---|---|---|
| `a_pex_buck` | `gen_pex_buck.py --topology grid` (default) | matrix factorisation + (in principle) BSIM4 device eval | 12100-node synthetic RC decoupling mesh + 60 BSIM4 (level=54) finger MOSFETs (30 HS + 30 LS), ~12200 unknowns |
| `e_pex_tree` | `gen_pex_buck.py --topology tree` | same power stage/BSIM4 fingers as `a_pex_buck`, but a tree-shaped (not grid) parasitic net -- see below | 11111-node tree net (branch=10, depth=4) + local-mesh loops + coupling caps, same 60 BSIM4 fingers |
| `b_long_switch` | (sed from `refs/r4_pcm_buck.cir`, see below) | long-transient timestep/output overhead, B-source (`PTeval`) cost | 20ms / ~10000 switching periods, no BSIM4 (smooth B-source switches, as r4) |
| `c_pvt_loop` / `c_pvt_separate` | `gen_pvt.py` | many-short-points fixed cost (process launch vs single-session loop) | 50 points (5 process x 5 Vin x 2 temp), ideal-switch buck, 300us/point |
| `d_analog_block` | `gen_analog_block.py` | pure BSIM4 device-evaluation load, small matrix | 60 independent 5T-OTA cells = 300 BSIM4 instances (NMOS+PMOS), 2us transient |
| `d_analog_block_long` | `gen_analog_block.py --tstop-ns 50000` | same as `d_analog_block`, stretched to a >=10s wall-clock run (round-1's 2us/0.6s deck is too short for a stable OMP-schedule signal) | same 300 BSIM4 instances, 50us transient (25x longer) |
| `f_analog_block_bsim3` | `gen_analog_block.py --device bsim3` | same 5T-OTA shape as `d_analog_block`, BSIM3 (level=49) instead of BSIM4 -- exercises `b3ld.c`'s OMP loop, not `b4ld.c`'s | 60 cells = 300 BSIM3 instances, 2us transient (bit-identical regression guard, too short for a performance signal -- see below) |
| `f_analog_block_bsim3_long` | `gen_analog_block.py --device bsim3 --n-cells 120 --tstop-ns 50000` | same as `f_analog_block_bsim3`, stretched AND widened for a stable OMP-schedule signal | 120 cells = 600 BSIM3 instances, 50us transient |
| `g_ad_stress` | `gen_ad_stress.py` | B-source parser/evaluator function coverage (forward-mode-AD correctness, not a performance benchmark) | 58 B-sources, one per `PT_*`/`PTF_*` node type/operator the parser supports, each argument PWL-ramped, 290 `.meas` points |

**Known limitation, recorded here rather than hidden** (see
`research/transient-acceleration.md` section 2): `a_pex_buck`'s regular
110x110 grid mesh is a near-worst-case topology for a general sparse direct
solver without nested-dissection ordering (no METIS in ngspice's KLU
binding), so on this deck `klu_refactor` alone is ~77% of CPU time and BSIM4
device evaluation is under 0.5% -- the *opposite* of "device evaluation
dominates" the deck was built to demonstrate. A real PEX-extracted parasitic
network is much closer to tree-shaped and would likely order far better.
Fixing the generator to build a tree/hierarchical mesh is the top "not done"
item for this deck (research doc section 5, item 2). `d_analog_block` (no
big linear system, 300 real BSIM4 instances) is the deck that actually shows
device-eval dominance (78.6% `BSIM4LoadOMP`, profiled).

### `a_pex_buck` -- `bench/gen_pex_buck.py`

```
bench/gen_pex_buck.py --mesh-n 110 --hs-fingers 30 --ls-fingers 30 --tstop-us 25
```

Power stage / type-III compensator topology as `refs/r3_vm_buck.cir` (see
that file for the design derivation) but the HS/LS switches are 30-finger
BSIM4 (level=54) arrays (a plausible, uncalibrated inline model card, same
minimisation style as `tests/fixtures/stb3_bsim4_cgd.cir`) instead of
B-source ideal switches, and a synthetic N x N RC decoupling mesh (trace
resistance + plane capacitance to ground, one coupling resistor onto
`vout`) is added for matrix size. `--tstop-us 25` (not settled -- this
deck's ~200+ switching-period settling time is far longer; 25us is a
tractable-turnaround slice of the same workload shape, not a full run).

### `e_pex_tree` -- `bench/gen_pex_buck.py --topology tree` (card #478 T9.2 task 2)

```
bench/gen_pex_buck.py --topology tree --hs-fingers 30 --ls-fingers 30 --tstop-us 25 --out bench/decks/e_pex_tree.cir
```

Identical power stage, compensator, and 30+30 BSIM4-finger switches as
`a_pex_buck` -- the only thing that changes is the parasitic network:
`a_pex_buck`'s regular NxN grid mesh is replaced by `tree_lines()` (in
`gen_pex_buck.py`, see its docstring), a tree-shaped net built to look more
like what a real PEX extraction tool produces (per-net RC trees from the
routing, not a lattice -- research/transient-acceleration.md section 2's
"known limitation" of the grid). Structure: `branch`-way fan-out (default
10) `depth` levels deep (default 4) from one root coupled onto `vout`, each
edge a series trace resistor and each node a capacitor to ground, both
scaled by level (resistance grows, capacitance shrinks, deeper into the
net -- an Elmore-tree shape, not uniform); plus a bounded, deterministic
number of "local mesh" resistors between sibling nodes (small loops, not
through the parent -- standing in for strapped/meshed routing segments)
and a deterministic set of small "coupling caps" between different
subtrees at the deepest level (adjacent-track capacitive coupling
stand-in). Fully deterministic, no RNG/seed. Default args give 11111 nodes
(branch=10, depth=4: `(10^5-1)/9`), close to `a_pex_buck`'s 12100 for a
fair matrix-size comparison.

**Result (card #478 T9.2, single run, `aaba50ba3f49-accel1`, same power
stage/BSIM4 fingers as `a_pex_buck`): 3.6s wall clock vs `a_pex_buck`'s
~50-55s -- roughly 14-15x faster, topology change only, zero source code
involved.** This is not a small effect: it directly confirms
research/transient-acceleration.md section 2's diagnosis that
`a_pex_buck`'s regular grid is a near-worst-case topology for KLU's
AMD/COLAMD-family fill-in (no nested-dissection/METIS option wired in),
and that `a_pex_buck` as originally built was measuring solver-ordering
pathology, not a representative PEX net. `e_pex_tree` is the fairer stand-in
for "device evaluation dominates a PEX-sized deck" that `a_pex_buck` was
meant to be; both decks are kept (not replacing `a_pex_buck`) since the grid
shape is itself now a useful adversarial/worst-case regression check.

### `b_long_switch` -- derived from `refs/r4_pcm_buck.cir`

Not a generator script (the base circuit already exists and is validated,
card #450/#455) -- mechanically derived by `sed` changing only `.tran 10n 6m
0 uic` -> `.tran 10n 20m 0 uic` and the final/mid `.meas` windows to match
(19998u/20000u, 19990u/20000u, 9990u/10000u), plus wrapping the `.tran` in
`rusage cputime` calls. Reproduce with:

```sh
sed -e 's/^tran 10n 6m 0 uic/tran 10n 20m 0 uic/' \
    -e 's/FROM=5998u TO=6000u/FROM=19998u TO=20000u/' \
    -e 's/FROM=5990u TO=6000u/FROM=19990u TO=20000u/g' \
    -e 's/FROM=2990u TO=3000u/FROM=9990u TO=10000u/' \
    -e 's#\.\./stb/lgprobe\.lib#../../stb/lgprobe.lib#' \
    refs/r4_pcm_buck.cir > bench/decks/b_long_switch.cir
```
(then hand-add the header comment and the two `rusage cputime` lines and
redirect the `write`/`wrdata` output paths under
`~/Work/data/ngspice_augmentation/accel/bench/b_long_switch/`).

### `c_pvt_loop` / `c_pvt_points/pt_NNN.cir` -- `bench/gen_pvt.py`

```
bench/gen_pvt.py --tstop-us 300
```

50-point grid (5 `gon_scale` values [switch-Ron process stand-in, this deck
has no real semiconductor model] x 5 `vin_v` values x 2 `.temp` values,
chosen to factor to exactly 50), same power stage/compensator style as
`refs/r3_vm_buck.cir` trimmed to 300us and with the loop-gain probe dropped
(not needed for a wall-clock benchmark). Two forms of the *same* grid:
`pvt_points/pt_000.cir` .. `pt_049.cir` (50 separate netlists, run as 50
separate processes -- the "many short points" shape) and `c_pvt_loop.cir`
(one ngspice session, `alterparam` + `option temp=` + `reset` + `run` +
`meas` per point, 50 times in a row -- the amortised-setup shape). Baseline
numbers already reproduce the archived project's own finding qualitatively:
50 separate processes serially = 5.5s, the same 50 points in one session =
3.9s (~30% less) purely from not re-paying process/parse startup 50 times.

### `d_analog_block` -- `bench/gen_analog_block.py`

```
bench/gen_analog_block.py --n-cells 60
```

60 independent 5-transistor OTA cells (diff pair + PMOS mirror load + NMOS
tail current source -- textbook, not any real op-amp design), each with its
own small differential input step, sharing global Vdd/bias/ground rails =
300 BSIM4 instances across 2 `.model` cards (nch4 NMOS, pch4 PMOS). Chosen
as a *parallel array of small independent cells* rather than one large
multi-stage op-amp/bandgap specifically to keep convergence risk low while
still giving many BSIM4 evaluations per Newton iteration -- the property
the task asked this deck to stress.

### `d_analog_block_long` -- `bench/gen_analog_block.py --tstop-ns 50000` (card #478 T9.2 task 3)

```
bench/gen_analog_block.py --n-cells 60 --tstop-ns 50000 --out bench/decks/d_analog_block_long.cir
```

Identical circuit to `d_analog_block` (same 60 cells / 300 BSIM4
instances) with `--tstop-ns` stretched from 2000 (2us, ~0.6s wall) to
50000 (50us, ~15s wall -- verified, not assumed) -- round 1's own
`d_analog_block` finished in well under a second, too short for a hardcoded
OMP-schedule variant's effect to separate from run-to-run noise (task 3
asked for >=10s). The per-cell input `PULSE` waveform already repeats every
2us (`PER=2000n`), so the extra 24 periods are the same kind of switching
work repeated, not a longer settle/DC tail -- every rep does real,
representative device evaluation, not idle time.

### `f_analog_block_bsim3` / `f_analog_block_bsim3_long` -- `bench/gen_analog_block.py --device bsim3` (card #483 T9.3 task 2)

```
bench/gen_analog_block.py --n-cells 60 --tstop-ns 2000 --device bsim3 --out bench/decks/f_analog_block_bsim3.cir
bench/gen_analog_block.py --n-cells 120 --tstop-ns 50000 --device bsim3 --out bench/decks/f_analog_block_bsim3_long.cir
```

Same 5T-OTA topology, sizes and `.tran`/`.meas` structure as
`d_analog_block`/`d_analog_block_long` -- only the `.model` cards differ
(`gen_analog_block.py --device {bsim4,bsim3}`, added this round; `bsim4`
remains the default, byte-identical to before). BSIM3 model card
(`level=49 version=3.3.0`, minimal `tox`/`nch`/`nsub`/`vth0`/`u0`/`vsat`
parameters, same style as this fork's own checked-in
`examples/svg/nmos_out_BSIM330_ps.sp`) exercises `b3ld.c`'s `#pragma omp
parallel for` (candidate 0105) instead of `b4ld.c`'s.

**`f_analog_block_bsim3` (60 cells/300 instances, 2us) is a bit-identical
regression guard only, not a performance benchmark** -- like round 2's
original `d_analog_block` before it grew a `_long` variant, it finishes in
well under a second, too short for an OMP-schedule effect to separate from
noise (measured: +5.9%, not distinguishable from run-to-run variation).

**`f_analog_block_bsim3_long` needed to be both longer AND bigger than the
BSIM4 equivalent to show a stable, above-10% signal** -- this is new
information this round, not assumed from `d_analog_block_long`'s 300-
instance/10.4% result: at 300 instances (60 cells, matching
`d_analog_block_long`'s convention exactly), 10 interleaved A/B reps
(2 batches of 5, order-swapped) gave only +8.7%/+5.6% (~+7.7% combined) --
real and repeatable, but under `accel_wallclock`'s +10% bar. Doubling to
120 cells / 600 instances (this file's current size) gave a clean +12.7%,
n=5. Plausible reading, not confirmed further this round: BSIM3's model
equations are simpler/cheaper per instance than BSIM4's, so the same
fork/join overhead per parallel region needs more total instance-work to
amortise before `schedule(guided)`'s rebalancing shows through as clearly.

### `g_ad_stress` -- `bench/gen_ad_stress.py` (card #486 T9.4 task 1/3)

```
bench/gen_ad_stress.py
```

One B-source per `PT_*`/`PTF_* `node type and operator
`src/spicelib/parser/inpptree.c`'s `PTdifferentiate()` handles (58 rows --
see the generator's own header for the full list), each argument driven by
an independent PWL-ramped voltage source rather than a literal constant.
This matters specifically for the forward-mode-AD candidate (0106,
research/transient-acceleration.md section 9): `mkb()`/`mkf()`
constant-fold a literal-only expression (e.g. `sin(1.5)`) into a single
`PT_CONSTANT` node at PARSE time, before it ever reaches the runtime
evaluator (`IFeval()`/`PTeval()`/`PTevalDual()`) at all -- so an existing
literal-only parser regression test
(`tests/regression/parser/bxpressn-1.cir`) does NOT exercise the code path
this candidate changes, despite looking like a natural stress deck for it.
Every argument here is a real `PT_VAR`-rooted subtree with a live
gradient instead. A `.nodeset` line seeds every ramp's t=0 value: without
it, ngspice's default zero Newton initial guess is out of domain for
`acosh` (`x>=1`), which -- checked directly on the unmodified baseline,
not assumed -- causes gmin/source-stepping to fail finding an operating
point at all, a pre-existing ngspice limitation unrelated to any patch in
this repo. This deck is a value-level regression/crash/coverage check, not
by itself proof that the AD candidate's *derivatives* agree with the
symbolic path (a B-source's value is computed identically regardless of
whether its derivative is right, in both code paths) -- see the research
doc for the direct derivative-vs-derivative evidence, gathered separately
with a throwaway self-check instrumented build.

## `runner.py`

```
bench/runner.py --ngspice <prefix>/bin/ngspice-aug --all --n 5 --label <name>
bench/runner.py --ngspice <prefix>/bin/ngspice-aug --deck a_pex_buck --n 5 --label <name>
```

Each run: `systemd-run --user --scope -p MemoryMax=<cap> -- /usr/bin/time -v
ngspice-aug -b <deck>.cir`, memory caps per deck (6G for `a_pex_buck`, 2G for
the rest, 1G per point for `c_pvt_separate`). Records wall clock (from
`/usr/bin/time -v`), user/sys CPU seconds, max RSS, the deck's own `rusage
cputime` phase-split deltas (already in every deck's `.control` block,
bracketing the `run`/`tran`), every named `.meas`/`print` value (for
`accel_same_results`), and `uptime` load average at the moment of the run
(other seats' workers may be running concurrently -- recorded, not
corrected for; medians of >=5 runs are used throughout, per spec.md
`accel_benchmarks`). `c_pvt_separate` is a special case: it runs all 50
`pvt_points/pt_NNN.cir` files as separate processes (serially by default,
`--pvt-parallel N` for N-way concurrency) and times the TOTAL wall clock to
finish all 50 -- that total is the metric for the many-short-points shape.

Output: JSON under
`~/Work/data/ngspice_augmentation/accel/bench/<deck>/results/<label>_<ts>.json`,
raw per-run logs under `.../<deck>/logs/`. Never under the repo (`no_data_in_repo`).

Only one candidate this round cleared both `accel_wallclock` bars: the raw
output encoding. It matters only for the one bench deck (`b_long_switch`)
that does a full `write ... .raw` dump; the other three decks only use the
much smaller `wrdata` (unaffected by `set filetype`), so they show no
change by construction, not by luck. Every other candidate is a genuine,
measured negative result -- see `research/transient-acceleration.md`
sections 4b and 5 for why, and for what is ranked to try next (forward-mode
AD for B-source `PTeval`, a tree-shaped PEX mesh generator so `a_pex_buck`
stops being solver-bound, and a hardcoded alternative OMP schedule instead
of `schedule(runtime)`).
